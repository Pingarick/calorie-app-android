# Движок рациона

Документ описывает, как приложение составляет рацион: какие данные нужны, как выбираются
блюда, как считается бюджет, что делает ИИ, а что алгоритм, и как это выглядит для человека.

## 1. Навигация

Четыре вкладки и чат кнопкой поверх них.

| Вкладка | Что внутри |
|---|---|
| **Рацион** (стартовая) | День и неделя, блюда по слотам, правки, «приготовил», статус бюджета |
| **Дневник** | Кольцо калорий, КБЖУ, фото, поиск, быстрый ввод, план против факта |
| **Покупки** | Корзина из рациона, цены, итог против бюджета, «уже есть дома» |
| **Профиль** | Цели, бюджет, время на готовку, семья, аллергии, «что я знаю» |

Чат не занимает вкладку: это инструмент, который открывается кнопкой на любом экране
и умеет менять рацион, корзину и настройки.

Калории остаются, но как отдельная вкладка. В рационе они показываются только как
индикатор сбалансированности дня, а не как главный экран.

## 2. Кто что делает

Рацион не генерируется целиком языковой моделью. Это гибрид: алгоритм гарантирует цифры,
модель даёт содержательные вещи.

| Задача | Кто решает | Почему |
|---|---|---|
| Баланс калорий и БЖУ по 28 слотам недели | алгоритм | модель не удержит сумму и белок на семи днях |
| Бюджет и переиспользование продуктов | алгоритм | требует перебора и точной арифметики |
| Разнообразие и «давно не готовили» | алгоритм (score) | считается из истории, а не из воздуха |
| Новые блюда и рецепты | модель | это генерация текста и идей |
| Понимание просьб («подешевле», «с рыбой в пятницу») | модель | разбор намерения |
| Объяснение выбора | модель | короткий текст на готовых фактах |
| Правки рациона | модель + алгоритм | модель вызывает действие, алгоритм пересчитывает |

Правило: любая цифра в интерфейсе посчитана кодом. Модель не имеет права называть
калорийность, цену или вес, которых нет в базе.

## 3. Что нужно на входе

| Данные | Откуда | Обязательность |
|---|---|---|
| Цель, норма ккал, БЖУ | профиль, формула Миффлина | да |
| Аллергии, диета | профиль | да |
| Вкусы (веса по блюдам, продуктам, кухням) | свайпы + история | да |
| Бюджет на неделю | профиль | нет |
| Время на готовку по дням | профиль | нет |
| Состав семьи и порции | профиль | нет |
| Продукты дома | «холодильник» или чек | нет |
| Цены и магазины | ручной ввод, чек, кэш | нет, без них бюджет выключается |
| Календарные правила (пост, праздники, гости) | профиль | нет |

Без цен бюджет просто не считается. Без вкусов работает нейтральный рацион с нулевыми весами.

## 4. Конвейер генерации

Пять шагов. Первые три быстрые и выполняются при любом изменении, четвёртый — по требованию.

### Шаг 1. Снимок контекста

Фиксируется на момент генерации: цели, бюджет, время по дням, что есть дома, последние
21 день готовки, календарные правила, текущие веса предпочтений. Всё в одном объекте,
он же попадает в кэш как стабильный префикс.

### Шаг 2. Пул кандидатов

Для каждого слота (завтрак, обед, ужин, перекус) собираются блюда, прошедшие жёсткие фильтры:

- нет аллергенов и запретов диеты;
- есть все продукты в доступности;
- время готовки укладывается в лимит дня;
- есть техника (духовка, плита, мультиварка);
- цена порции не выше дневного лимита.

Дальше каждое блюдо получает score:

    score = 1.0 * предпочтения
          + 0.8 * новизна
          - 1.2 * недавний_повтор
          - 0.7 * относительная_цена
          - 0.5 * сложность
          + 0.4 * сезонность
          + 0.6 * попадание_в_остаток_КБЖУ
          + 0.5 * соответствие_слоту

Остаётся топ-40 на слот. Это важно: модель и алгоритм видят не тысячи блюд, а короткий
список уже допустимых.

### Шаг 3. Сборка недели

Задача: заполнить 7 дней по 3-4 приёма пищи так, чтобы суммарно сходились калории,
белок, бюджет и разнообразие. Это оптимизация с ограничениями, а не выбор по одному блюду.

Целевая функция:

    максимизировать  Σ score(блюдо, слот)
    минус  штраф_за_перерасход_бюджета
    минус  штраф_за_повтор (блюдо больше 2 раз в неделю)
    минус  штраф_за_однообразие (меньше 3 кухонь за неделю)
    плюс   бонус_за_остатки (ужин на 2 порции закрывает завтрашний обед)

Ограничения:

- калории дня в пределах ±5% от цели;
- белок не ниже 90% цели;
- бюджет недели не превышен (если пользователь не разрешил перебор);
- время готовки в день не больше доступного;
- порция в диапазоне 0.5-2.0 от базовой;
- блюдо не чаще 2 раз в неделю.

Метод: жадная инициализация по score, затем локальный поиск (перестановки и замены порций,
несколько тысяч итераций). На телефоне это миллисекунды, на бэкенде — тем более.
Решение детерминировано: одинаковый вход и seed дают одинаковую неделю. Кнопка
«пересобрать» меняет seed и показывает diff.

Почему не просить модель «сделай неделю»: она не удержит одновременно 28 слотов,
сумму калорий, белок, бюджет и разнообразие. Даже если ответ выглядит красиво,
проверка покажет расхождение в 20-30%.

### Шаг 4. Рецепты

Для каждого блюда берётся рецепт из кэша. Если его нет — модель генерирует рецепт
по контракту:

    {
      "dish": "Куриная грудка с гречкой и овощами",
      "servings": 2,
      "time_min": 25,
      "technique": "плита",
      "ingredients": [
        {"product_id": "chicken_breast", "grams": 300},
        {"product_id": "buckwheat", "grams": 160},
        {"product_id": "carrot", "grams": 120}
      ],
      "steps": [
        {"order": 1, "text": "Промыть гречку, залить водой 1:2, варить 15 минут."},
        {"order": 2, "text": "Грудку нарезать, обжарить 8-10 минут.", "timer_min": 10}
      ]
    }

Валидатор до показа проверяет:

- все `product_id` существуют в каталоге;
- сумма КБЖУ из ингредиентов совпадает с заявленной в блюде (±10%);
- граммовки в разумных пределах (порция 150-800 г, специи до 20 г);
- шаги не пустые, время соответствует сложности;
- нет аллергенов.

Не прошло — один retry с перечнем ошибок, потом фолбэк на блюдо из каталога с готовым рецептом.
Придуманное моделью блюдо после валидации кэшируется и становится частью каталога.

### Шаг 5. Корзина и бюджет

Все ингредиенты недели суммируются по продуктам, вычитается то, что уже есть дома,
и группируется по отделам магазина. Считается цена и итог.

Если итог выше бюджета, запускается починка: самые дорогие блюда меняются на более дешёвые
аналоги того же слота с близкой калорийностью. Починка повторяется, пока не сойдётся
или пока не останется вариантов. В последнем случае показывается честный diff:
«бюджет превышен на 340 ₽, вот что можно убрать».

## 5. Логика дня и остатков

- Калорийность распределяется по слотам: завтрак 25%, обед 35%, ужин 30%, перекус 10%.
  Доли настраиваются.
- Блюдо, приготовленное на 2 порции, закрывает ужин и следующий обед как «остатки».
  Это экономит время, деньги и снижает число готовок.
- Batch cooking: одна готовка в воскресенье может закрыть 2-3 приёма пищи.
- Если день перегружен (нет времени), алгоритм ставит блюдо с минимальным временем
  или остатки, даже если score ниже.
- «Не готовлю» — слот помечается как еда вне дома и исключается из корзины.

## 6. Правки и пересборка

Правка — это не текст, а операция:

| Действие | Что происходит |
|---|---|
| Заменить блюдо | из пула того же слота, ближайшее по калориям |
| Убрать | слот остаётся пустым или закрывается перекусом |
| Добавить из истории | блюдо из архива с пересчётом порции |
| Поменять порцию | пересчёт КБЖУ и корзины |
| Перенести на другой день | проверка лимитов времени и калорий |
| Заблокировать | блюдо не трогается при пересборке |
| «Не сегодня» | откладывает и понижает вес блюда |

После правки пересчитываются день, неделя и корзина — дельтой, а не с нуля.

Пересборка недели всегда показывает diff: что изменилось и почему. Молчаливая замена
раздражает сильнее, чем плохой рацион.

## 7. Связь с дневником

- «Приготовил» переносит блюдо в дневник с граммовками и КБЖУ, сохраняя ссылку на план.
- Если человек поел не по плану, дневник фиксирует факт, план остаётся для сверки.
- Разница план/факт за неделю — метрика приверженности.
- Остатки учитываются: приготовил 2 порции, съел одну — вторая доступна на следующий день.

## 8. Чат

Модель возвращает не текст, а намерение:

    {"action": "set_budget", "amount": 4000, "period": "week"}
    {"action": "require_dish", "day": "friday", "tag": "fish"}
    {"action": "replace_meal", "day": "tuesday", "slot": "dinner", "reason": "быстро"}
    {"action": "exclude_product", "name": "кинза"}

Код валидирует действие, применяет его и пересчитывает рацион. Если действие нарушает
ограничения (аллергия, бюджет), приложение отвечает причиной, а не применяет молча.

## 9. Производительность и стоимость

- Первый рацион: 3-8 секунд, потому что рецепты либо в кэше, либо генерируются пачкой.
- Пересборка без новых блюд: меньше секунды, модель не вызывается.
- Неделя с 20 новыми рецептами: около 20 запросов, порядка $0.02.
- Повторные недели почти бесплатны: каталог пополняется, рецепты кэшируются.
- Планировщик получает компактный срез каталога (60-120 продуктов), а не всю базу.

## 10. Отказы и деградация

Порядок ослабления ограничений, если решение не находится:

1. бюджет;
2. разнообразие;
3. время готовки;
4. точность калорий;
5. никогда — аллергии и диета.

Что показать, если сети нет: последний рацион, рецепты и корзину из кэша. Генерация
нового рациона требует сети, если нужны новые рецепты; из готового каталога алгоритм
соберёт неделю офлайн.

## 11. Метрики

| Метрика | Зачем |
|---|---|
| доля рационов, которые реально готовят | главный показатель пользы |
| доля принятых советов | качество персонализации |
| правок на рацион | если много — алгоритм не угадывает |
| превышение бюджета | точность цен |
| время до первого рациона | первый опыт |
| стоимость генерации на пользователя | экономика |

## 12. Что меняется в текущем приложении

1. Вкладка «Рацион» становится стартовой, дневник уезжает во вторую вкладку.
2. Добавляются таблицы: продукт, цена, блюдо, ингредиент, рецепт, рацион, слот, предпочтение, событие.
3. Появляется локальный движок score и сборки недели на Kotlin, без сети.
4. Vision остаётся в дневнике, провайдер DeepSeek уже подключён.
5. Ручной ввод расширяется: поиск по каталогу, свой продукт, быстрый ввод без выбора.
